# Как самостоятельно обновить kvaterka.by

Этот файл — пошаговая инструкция для человека без опыта администрирования
серверов. Она описывает **реальный** процесс, которым сайт был развёрнут и
обновлялся на практике (а не теоретическую схему) — включая грабли, на которые
мы уже наступили, чтобы вам не пришлось наступать на них снова.

Если вы работаете с Claude Code (или любым другим ассистентом-разработчиком) —
просто покажите ему этот файл и скажите «обнови сайт по инструкции». Если
делаете это руками — читайте по порядку, ничего не пропуская.

---

## 0. Общая картина

```
Ваш компьютer (Windows)                 Хостинг HostFly (cPanel)
──────────────────────                  ──────────────────────────
Код на D:\kvaterka.by         git push  /home/kvaterk1/kvaterka
  └─ npm run build  ──────────────────▶   ├─ исходный код (git)
       (.next)                            ├─ .next  ← собранное приложение
       │                                  ├─ node_modules
       │  zip + загрузка через            ├─ tmp/restart.txt ← перезапуск
       └─ File Manager ──────────────▶    └─ PostgreSQL (localhost)
```

**Ключевой факт, из-за которого процесс именно такой:** собрать приложение
(`npm run build`) прямо на этом хостинге **нельзя** — аккаунт упирается в
лимит процессов/потоков (CloudLinux LVE), и сборщик (SWC) падает с ошибкой
`ThreadPoolBuildError`. Поэтому сборка всегда делается **на вашем компьютере**,
а на сервер загружается уже готовый результат (`.next`).

Два вида обновлений:

- **Только код фронтенда/бэкенда** (новая страница, исправление бага, текст) —
  нужно и обновить исходники на сервере (`git pull`), и пересобрать `.next`
  локально, и залить `.next` на сервер. Полный процесс — раздел 2.
- **Только собранный `.next`** (например, вы уже поменяли код и запушили, но
  забыли обновить сервер) — можно ограничиться шагами 2.5–2.9.

## 2. Полное обновление, шаг за шагом

### 2.1 Получить последний код на своём компьютере

```bash
cd D:\kvaterka.by
git pull
npm install
```

`npm install` нужен, если в `package.json` появились новые зависимости — если
запустить и ничего не изменилось, команда просто ничего не сделает.

### 2.2 Внести изменения в код

Сделать нужные правки, закоммитить и запушить в GitHub:

```bash
git add -A
git commit -m "описание изменения"
git push
```

### 2.3 Обновить исходный код на сервере

cPanel → **Terminal** (в левом меню). В терминале:

```bash
cd ~/kvaterka
git pull
```

Если в `package.json` появились новые зависимости:

```bash
npm install --include=dev
```

**Важно:** флаг `--include=dev` обязателен — на этом хостинге обычный
`npm install` почему-то не ставит dev-зависимости, а один из пакетов
(`@tailwindcss/postcss`) нужен даже для чтения `next.config.mjs`. Без него
сборка (если бы она вообще запускалась на сервере) падает с
`Cannot find module '@tailwindcss/postcss'`.

**Ловушка этого хостинга (DEC-087).** `npm install` здесь может ответить
«up to date in 1s», хотя в `node_modules` стоит **более старый** `next`, чем
записано в `package-lock.json` — а исправления безопасности Next.js живут именно
в `node_modules/next` на сервере, а не в загружаемой папке `.next`. Проверка:

```bash
node -p "require('next/package.json').version"
grep -A1 '"node_modules/next"' package-lock.json
```

Если версии разные — поставить нужную точечно, не меняя `package.json` и lock:

```bash
npm install --no-save --include=dev next@<версия из package-lock.json>
```

Если добавлены новые миграции базы данных (`scripts/migrate.ts`,
файлы в `db/migrations/`):

```bash
cd ~/kvaterka
export $(cat /dev/null) # заглушка, переменные окружения уже в процессе cPanel
npm run db:migrate
```

Если команда ругается на отсутствие `DATABASE_URL` — переменные окружения
приложения на этом хостинге хранятся не в файле `.env`, а в конфигурации
cPanel Node Selector. Посмотреть их можно так:

```bash
cat ~/.cl.selector/node-selector.json
```

и временно экспортировать перед разовой командой:

```bash
export DATABASE_URL="<значение DATABASE_URL из файла выше>"
npm run db:migrate
```

### 2.4 Собрать приложение — ЛОКАЛЬНО, не на сервере

На своём компьютере:

```bash
cd D:\kvaterka.by
npm run build
```

Дождаться `✓ Compiled successfully`. Если сборка падает — чинить локально,
на сервер ничего не грузить, пока `npm run build` не пройдёт чисто.

### 2.5 Упаковать `.next` в zip

```powershell
cd D:\kvaterka.by
.\deploy\make-deploy-zip.ps1
```

Скрипт сам:
- копирует `.next` во временную папку, **исключая** `.next\cache` (это кэш
  сборщика, десятки–сотни МБ, серверу не нужен и только замедляет загрузку);
- упаковывает в `deploy\kvaterka-build.zip`;
- печатает итоговый размер (обычно 2–4 МБ).

(Если скрипта `deploy\make-deploy-zip.ps1` почему-то нет — воспроизвести
вручную командой из `deploy/make-deploy-zip.ps1`, там всё закомментировано.)

### 2.6 Загрузить zip на сервер

1. cPanel → **File Manager**.
2. Слева в дереве папок раскрыть `kvaterka` (стрелочкой) и **кликнуть по
   названию папки** `kvaterka`, чтобы открыть её содержимое.
   ⚠️ **Не открывайте папку двойным кликом по имени в списке файлов справа** —
   в этой версии File Manager двойной клик по папке включает режим
   переименования, а не открывает её. Только через дерево слева.
3. Кнопка **«Загрузить»** (Upload) в верхнем меню.
4. Выбрать файл `D:\kvaterka.by\deploy\kvaterka-build.zip` и дождаться
   100% / «Upload Complete».
5. Вернуться в File Manager (кнопка «Go Back to ...» или заново открыть папку
   `kvaterka` через дерево слева).

### 2.7 Распаковать

1. В списке файлов найти `kvaterka-build.zip`, кликнуть по нему один раз
   (выделить).
2. В верхнем меню — **«Извлечь»** (Extract).
3. В открывшемся окне путь для распаковки должен быть **`/kvaterka`**
   (это и есть `/home/kvaterk1/kvaterka`, corень приложения) — так и оставить.
4. Нажать **Extract Files**.
5. Появится окно с логом — должны идти строки вида
   `inflating: .next/app-build-manifest.json`, `inflating: .next/server/...`
   и т.д. Это означает, что старая папка `.next` на сервере перезаписывается
   новой.
6. Закрыть окно результатов.
7. Можно удалить `kvaterka-build.zip` из File Manager после распаковки —
   он больше не нужен (но и не мешает, если оставить).

### 2.8 Перезапустить приложение

Сервер работает не как обычный процесс, а через LiteSpeed/Passenger — он
следит за файлом-триггером и перезапускается, когда этот файл обновляется.

cPanel → **Terminal**:

```bash
mkdir -p ~/kvaterka/tmp
touch ~/kvaterka/tmp/restart.txt
```

Перезапуск занимает несколько секунд — сайт коротко «подвисает» на первый
запрос после этого (приложение заново стартует), дальше работает как обычно.

### 2.9 Проверить, что всё работает

```bash
sleep 5
curl -s -o /dev/null -w "HTTP:%{http_code}\n" https://kvaterka.by/
```

Должно быть `HTTP:200`. Дальше — глазами в браузере:

- Открыть `https://kvaterka.by/` — главная страница грузится, без ошибок.
- Переключить язык (RU/BE/EN) в шапке — переводится корректно.
- Переключить тёмную тему — переключается, ничего не «слепнет».
- Зайти в раздел, который меняли, и проверить именно то, что чинили/добавляли.
- Открыть консоль браузера (F12 → Console) на паре страниц — не должно быть
  красных ошибок.

Если что-то не так — см. раздел 4 «Если что-то пошло не так».

### 2.10 Один раз после обновления с DEC-085: перерегистрировать Telegram-webhook

Начиная с DEC-085 сайт принимает сообщения от Telegram-бота **только** если
Telegram присылает секретный заголовок. Раньше любой мог отправить поддельный
запрос и «подтвердить» чужой номер телефона. Секрет Telegram начнёт присылать
только после повторной регистрации webhook — без этого шага подтверждение
телефона и привязка Telegram перестанут работать.

Выполнить **один раз** на сервере (в каталоге проекта), подставив токен бота:

```bash
TELEGRAM_BOT_TOKEN=<токен бота> PUBLIC_BASE_URL=https://kvaterka.by npm run telegram:webhook
```

Должно напечатать `{"ok":true,"description":"Webhook was set",...}`. Повторять
нужно только при смене домена или токена бота. Проверка: отправить боту
`/status` — он должен ответить.

### 2.11 Быстрый путь: одна команда вместо шагов 2.3 (миграции), 2.7–2.10 и копии для отката

После `git pull`, `npm install --include=dev` (если менялись зависимости) и
загрузки `kvaterka-build.zip` в `~/kvaterka` (шаг 2.6) — в cPanel Terminal, в
каталоге проекта:

```bash
source ~/nodevenv/kvaterka/22/bin/activate
bash deploy/apply-release.sh
```

Скрипт делает всё в том порядке, при котором сайт не бывает «наполовину
обновлён»: 1) миграции (старый код спокойно работает на новой, только
добавленной схеме); 2) перерегистрация Telegram-webhook (новый код отвечает 401
на запросы без секретного заголовка); 3) копия `.next` в `.next.backup-…` и
распаковка zip; 4) `tmp/restart.txt` и проверка `/` и `/api/health`. Строка
подключения к базе и токен бота берутся из настроек Node.js-приложения cPanel и
**нигде не печатаются**. Любая ошибка останавливает скрипт до следующего шага:
упавшая миграция не даёт заменить сборку. `DRY_RUN=1 bash deploy/apply-release.sh`
только показывает шаги, ничего не выполняя.

## 3. Откат назад (если новая версия сломала сайт)

Каждый раз **перед** распаковкой новой версии имеет смысл сохранить копию
текущей рабочей:

cPanel → Terminal, **до** шага 2.7:

```bash
cd ~/kvaterka
cp -r .next .next.backup-$(date +%Y%m%d-%H%M)
```

Если новая версия оказалась хуже:

```bash
cd ~/kvaterka
rm -rf .next
mv .next.backup-ГГГГММДД-ЧЧММ .next
touch tmp/restart.txt
```

(подставить реальное имя папки бэкапа — посмотреть через `ls -d .next.backup-*`)

## 4. Если что-то пошло не так

### Сайт отдаёт 502/503 или не открывается после распаковки

Почти всегда — приложение ещё не успело перезапуститься, или процесс упал при
старте. Подождать 10–15 секунд и проверить снова. Если не помогает:

```bash
cd ~/kvaterka
touch tmp/restart.txt
sleep 8
curl -s -o /dev/null -w "HTTP:%{http_code}\n" https://kvaterka.by/
```

Логи приложения (если доступны в этой панели): cPanel → «Настройка Node.js
приложений» → выбрать приложение → там обычно есть ссылка на лог-файл, либо
искать `~/kvaterka/*.log` / `~/logs/` через Terminal.

### `npm install` или `npm run db:migrate` на сервере падают

Не пытайтесь запускать `npm run build` на сервере — он гарантированно упадёт
(см. раздел 0). `npm install` и `npm run db:migrate`, наоборот, безопасны и
нужны при обновлении зависимостей/схемы.

Если `npm run db:migrate` пишет «Schema is current» — это нормально, значит
новых миграций нет, ничего делать не нужно.

### Не открывается File Manager / зависает загрузка

Обновить страницу cPanel, попробовать другой браузер. Если файл больше
~50–100 МБ — загрузка через File Manager может быть медленной или обрываться;
в таком случае лучше загружать по SFTP (данные — cPanel → «FTP-аккаунты» или
использовать данные основного аккаунта cPanel с SFTP на порт 22).

## 6. Административная панель сайта

Раздел для персонала (модерация, поддержка, финансы, админ) живёт на
`https://kvaterka.by/staff` (и `/moderation`, `/staff/users`, и т.д.).

**Важно про доступ:**

- Если у аккаунта нет ни одной служебной роли — `/staff` отдаёт обычную
  страницу 404, а не «доступ запрещён». Это осознанное решение (см.
  `src/ui/staff-shell.tsx`) — так посторонний не узнаёт, что такая панель
  вообще существует.
- Служебные роли (`ADMIN`, `MODERATOR`, `SUPPORT`, `VERIFIER`, `FINANCE`)
  **обязательно требуют двухфакторную аутентификац, (2FA)** — даже с верным
  паролем эти разделы останутся недоступны, пока не подключено приложение-
  аутентификатор (Google Authenticator, Authy и т.п.). Это включается один раз
  на странице `https://kvaterka.by/staff/security` после первого входа —
  показывается QR-код, сканируете телефоном, вводите 6-значный код для
  подтверждения.
- Пароли в базе хранятся как необратимый хеш (argon2id) — **ни я, ни кто-либо
  ещё не может «посмотреть» существующий пароль**, только сбросить на новый.

Логин администратора и первый пароль — см. отдельный файл
`ADMIN_ACCESS.md` рядом с этим (он НЕ загружен в git — хранится только
у вас локально).

## 7. Секреты и куда их не класть

- Пароли, `DATABASE_URL`, токены — никогда не коммитить в git. `.gitignore`
  уже исключает `.env*`, `deploy/*.zip` и дампы базы (`*.dump`).
- Файл `ADMIN_ACCESS.md` с логином/паролем администратора тоже добавлен в
  `.gitignore` — держите его копию в надёжном месте (менеджер паролей), а не
  просто на рабочем столе.
- Если пароль администратора когда-то «утёк» (кому-то показали, отправили не
  туда) — зайти под этим аккаунтом на `/dashboard/account` и сменить пароль,
  это сразу отзывает все его активные сессии.
